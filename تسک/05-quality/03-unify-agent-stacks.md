## هدف — مسئله‌ی معماری اصلی پروژه
سه stack موازی با سه پروتکل tool و سه مدل مجوز:
1. **Void chat** (`void/`) — ابزار native + KB + MCP (merge تا ۱۲۸ ابزار)
2. **NI workflow engine** (`neuralInverse/`) — پروتکل JSON-block، ابزار خودش
3. **Power Mode** (`powerMode/`, port از opencode) — ابزارهای خودش + bashSecurity

نتیجه: سه‌برابر هزینه‌ی نگهداری، ناسازگاری رفتار (مثلاً مجوز در chat با executor
فرق دارد)، و کندی توسعه‌ی هر قابلیت جدید (باید سه‌جا پیاده شود).

## طرح (تدریجی، بدون big-bang)
1. **فاز ۰ — سند:** `تسک/05-quality/architecture.md`: جدول «قابلیت × stack» و نقشه‌ی
   ادغام؛ توافق با upstream قبل از شروع (این تغییر structural است و PR بزرگی می‌شود)
2. **فاز ۱ — Tool Registry مشترک:** همه‌ی ابزارها به یک `ToolRegistry` مرکزی
   مهاجرت کنند (تعریف واحد: name/schema/permission tier/cwd-aware). سه stack فقط
   scope متفاوت می‌گیرند. این تک‌کار باگ‌های ناسازگاری ابزار را می‌کشد
3. **فاز ۲ — Permission مشترک:** خروجی A4 به تنها نقطه‌ی تصمیم تبدیل شود
4. **فاز ۳ — مسیر context مشترک:** یک pre-send pipeline واحد (همین که در C1 ساخته
   می‌شود) برای همه — system prompt + rules + memories + context pack در یک‌جا
5. **فاز ۴ — همگرایی پروتکل:** native-first (A2) به‌عنوان پروتکل استاندارد همه‌ی
   stack ها؛ JSON-block فقط لایه‌ی fallback مدل ضعیف
6. در هر فاز: رفتار کاربر فعلی نباید بشکند — با feature flag و migration guide
