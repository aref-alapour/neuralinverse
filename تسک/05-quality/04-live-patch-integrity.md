# Q4 — یکپارچگی live-patch (سکوت مرگبار را بشکن)

- **اولویت:** P0 — قبل از هر پورت جدید | **برآورد:** S/M | **وضعیت:** 🔴
- **وابستگی:** — (جایگزین و کامل‌کننده‌ی بند ۵ از [Q2](02-codebase-hygiene.md))
- **هم‌ارز در بازار:** ندارد — این ابزار مخصوص جریان کاری ماست

## چرا این تسک وجود دارد (شواهد، نه حدس)

در ممیزی ۲۰۲۶-۰۹-۰۵ روی برنامه‌ی نصب‌شده اندازه گرفتیم:

```
bundle نصب‌شده : 24,115,388 بایت
.orig (pristine): 24,115,040 بایت
اختلاف          : 348 بایت
globalThis.__niC=  →  ۰ مورد در bundle نصب‌شده
```

یعنی کامیت `2eb53a2` («live-patch port of context pipeline») در repo ثبت شده و
DoD اش تیک خورده، ولی ماژول `__niC` **هرگز روی برنامه‌ی نصب‌شده ننشسته**. سه فیکس
کوچک agent اعمال شده‌اند و همین. ماه‌ها روی نسخه‌ای تست شده که pipeline در آن نبود.

**شاهد مکمل (راستی‌آزمایی دوم):** نه‌فقط PREPEND، بلکه هیچ‌کدام از PATCH های وابسته
به آن هم اعمال نشده‌اند — call-site چت هنوز دقیقاً شکل دست‌نخورده‌اش را دارد:

```
__niC.  (ارجاع فراخوانی)                         → ۰ مورد
forSend / execCompact                            → ۰ مورد
__niOv                                           → ۰ مورد
prepareLLMChatMessages({chatMessages:k,…})       → ۱ مورد (pristine)
```

نتیجه‌ی دوگانه: (الف) برنامه‌ی نصب‌شده تمام این مدت **بدون هیچ compaction پیش از
ارسال** اجرا شده؛ (ب) چون هیچ ارجاع معلقی هم باقی نمانده، خطای runtime نداریم —
یعنی شکست کاملاً بی‌صدا بوده و هیچ نشانه‌ای در UI یا کنسول نمی‌داده. این دقیقاً
بدترین حالت ممکن است و توضیح می‌دهد چرا ماه‌ها کسی متوجه نشد.

ریشه‌اش یک خط در `tools/live-patch.py` است:

```python
if count == 0:
    print(f"SKIP  {name}: pattern not found" + ...)
    continue
...
return 0          # ← حتی وقتی هیچ پچی نگرفته، خروجی موفق است
```

اسکریپت **در هر حالتی exit 0 می‌دهد**. یک SKIP در میان ۳۰ خط لاگ گم می‌شود و
هیچ گیتی آن را نمی‌گیرد. این دقیقاً همان دروازه‌ی شماره ۴ `AGENTS.local.md` است که
فرض می‌کردیم دارد کار می‌کند.

## سه نقص مشخص

1. **شکست خاموش:** پچ‌نخوردن = موفقیت. exit code، شمارنده، و خلاصه‌ی پایانی وجود ندارد.
2. **`--verify` وجود ندارد.** در DoD تسک‌ها و در `AGENTS.local.md` به آن ارجاع داده شده،
   ولی `main()` فقط `--revert` را می‌شناسد (`argv` را چک کردیم). یعنی گیت ۴ عملاً
   قابل بررسی نیست.
3. **`.orig` بیات می‌شود:** `backup_once` فقط وقتی بکاپ می‌گیرد که `.orig` نباشد. بعد از
   هر آپدیت برنامه، `.orig` مال build قبلی می‌ماند و `--revert` یک bundle قدیمی را
   روی نسخه‌ی جدید می‌نویسد — یعنی خراب کردن نصب به‌جای برگرداندن آن.
   (الان خطر فعلی نیست: سایزها همخوانند، پس build عوض نشده — ولی یک آپدیت کافی است.)

## طرح پیاده‌سازی

### الف) manifest کنار برنامه
بعد از هر apply یک فایل `.ni-livepatch.json` در ریشه‌ی `resources/app` نوشته شود:

```json
{
  "appVersion": "<از product.json>",
  "repoCommit": "<git rev-parse --short HEAD>",
  "appliedAt": 1757000000,
  "bundleSha256Before": "…",
  "bundleSha256After": "…",
  "patches": [{ "name": "…", "sites": 2, "status": "applied|skipped|already" }],
  "prepends": [{ "name": "…", "sentinel": "globalThis.__niC=", "status": "injected" }]
}
```

### ب) exit code معنادار در حالت apply
- هر پچ سه حالت دارد: `applied` (الگوی قدیم پیدا و جایگزین شد) / `already` (الگوی جدید
  از قبل هست) / **`missing`** (هیچ‌کدام نیست).
- در پایان یک جدول خلاصه چاپ شود و اگر حتی یک `missing` باشد → **exit 1**.
- `--allow-missing` برای موارد آگاهانه (مثلاً upstream خودش فیکس کرده) که در manifest
  با دلیل ثبت می‌شود.

### ج) `--verify` واقعی
بدون تغییر دادن هیچ فایلی، برای هر PATCH و هر PREPEND بررسی کند که اثرش روی bundle
هست یا نه (برای PREPEND: وجود sentinel؛ برای PATCH: وجود رشته‌ی `new`).

> ⚠️ **تله‌ای که در عمل به آن خوردیم:** منطق ساده‌ی «اگر `old` هنوز هست ⇒ اعمال نشده»
> **غلط** است. سه پچ از ۲۹ تا از نوع **درج** اند، نه جایگزینی — یعنی `new` خودش
> شامل `old` است (`agents-tab: say why a run finished`، `intake: populate the field`،
> `main/impl: track finish_reason`). بعد از اعمال موفق، `old` همچنان به‌عنوان بخشی از
> `new` در فایل هست. یک verify ساده‌لوحانه این سه تا را «اعمال‌نشده» گزارش می‌کند و
> دقیقاً همان بی‌اعتمادی‌ای را می‌سازد که این تسک قرار است از بین ببرد.
>
> **قاعده‌ی درست:** اول `new in data` را چک کن ⇒ `applied`. فقط اگر `new` نبود و
> `old` بود ⇒ `pending`. اگر هیچ‌کدام نبود ⇒ `missing`. برای پچ‌های چندجایگاهی هم
> باید تعداد سایت‌های مورد انتظار در خود جدول PATCHES ثبت شود، وگرنه اعمال جزئی
> (۱ از ۲) قابل تشخیص نیست.

خروجی:

```
OK      agent-map-by-id                         1 site
OK      agent-conversation-memory               3 sites
MISSING conversation-compactor runtime module   sentinel globalThis.__niC= not found
...
2 OK, 1 MISSING  → exit 1
```

**معیار درستی این تسک:** اجرای `--verify` روی نصب فعلی، امروز، باید ماژول
`__niC` را `MISSING` گزارش کند. اگر سبز داد، خود `--verify` غلط است.

### د) تشخیص آپدیت برنامه
اگر `sha256` فعلی bundle نه با `bundleSha256After` منیفست بخواند و نه با `.orig`،
یعنی برنامه آپدیت شده. در این حالت:
- `apply` و `--revert` **متوقف شوند** با پیام روشن،
- `--rebaseline` ارائه شود که `.orig` را از bundle فعلی می‌سازد و manifest را ریست می‌کند.

### ه) `--status`
یک نمای یک‌صفحه‌ای: نسخه‌ی برنامه، کامیت repo موقع آخرین apply، جدول پچ‌ها، و اینکه
`.orig` تازه است یا بیات. این همان چیزی است که باید اول هر session نگاه کنیم
(هم‌راستا با بند ۳ پرامپت شروع در [`00-EXECUTION-PROMPT.md`](../00-EXECUTION-PROMPT.md)).

## معیارهای پذیرش

- [ ] `python tools/live-patch.py --verify` روی نصب فعلی، ماژول `__niC` را MISSING نشان می‌دهد و `exit 1` می‌دهد
- [ ] apply با یک الگوی عمداً خراب‌شده → جدول خلاصه + `exit 1`
- [ ] `.ni-livepatch.json` بعد از apply نوشته می‌شود و `--status` آن را درست می‌خواند
- [ ] شبیه‌سازی آپدیت برنامه (دست‌کاری bundle) → `--revert` جلوی خودش را می‌گیرد و `--rebaseline` را پیشنهاد می‌دهد
- [ ] `AGENTS.local.md` به‌روز: گیت ۴ = «apply سبز **و** `--verify` سبز»، نه فقط اجرا شدن اسکریپت
- [ ] بند ۵ [Q2](02-codebase-hygiene.md) به این تسک ارجاع داده و از آنجا حذف شود

## یادداشت

این تسک هیچ ربطی به Context Ledger ندارد ولی **پیش‌نیاز هر پورت زنده‌ی بعدی** است.
تا وقتی ابزار می‌تواند بی‌صدا هیچ‌کاری نکند و بگوید موفق شدم، هیچ «تست owner روی
نسخه‌ی نصبی» معتبر نیست.
